# 问题批注文档：识别与修复规范

LLM 生成的 wiki 中会沉淀两类**非知识页面**——它们不是知识内容，而是 llm_wiki 软件自动扫描/分析后批量生成的问题提示。它们会污染目录、拉低孤立页比例、干扰检索，需要专门修复。

## 零、执行时机：排在所有修复之前（优先级最高）

问题批注文档修复应作为**整个修复流程的第一步**，先于 `fix_links` / `fix_related` / `fix_frontmatter` / 合并：

1. **B 类批注内含重复与冲突线索**（「X 页与 Y 页可能重复」「命名冲突」等）——先按批注处理，可直接消化掉一批重复与命名问题，**减少后续 merge 候选与人工标注量**；
2. **清除 A 类占位页后**，`audit.py` 的孤立页/游离页统计不再被上千个占位页污染，后续报告与修复计划更准确；
3. **占位页删除会重写指向它的链接**——若放到流程最后，会把已合并过的链接再改一遍，徒增重写量与风险。

推荐次序：`scan_problem_annotations.py` → 修复批注页 → 复跑 `audit.py` → `fix_links` → `fix_related` → `fix_frontmatter` → 合并。

## 一、两类问题文档的识别特征

### A 类：Wiki Lint 占位页（stub placeholder）

**识别特征**（命中前两条即可判定）：
- frontmatter `tags` 含 `stub` 或 `lint`；
- 正文含固定句 `Created by Wiki Lint as a placeholder for a missing wikilink target.`；
- 伴随特征：`type: query`（即使在 concepts/entities 目录下也是 query）、`sources: []`、体积极小（实测中位约 250B，通常 <1KB）、title 是某个失效 wikilink 目标的可读形式。

**成因**：页面正文写了 `[[X]]`，而 X 没有对应页面（写法与实际 slug 不匹配、或该页从未创建），Wiki Lint 便自动建占位页。

**实测分布**（1534 个）：`queries` 747、`concepts` 474、`entities` 276、`comparisons` 12、`findings` 12、`sources` 8、`methodology` 4。

### B 类：Ingest 分析批注页（analysis annotation）

**识别特征**：
- 文件名 = **问题描述**（而非页面标题），常带时间戳后缀 `-YYYY-MM-DD-HHMMSS`（该特征不绝对）；
- frontmatter 极简：`tags: []`、`related: []`，常缺 `sources`/`updated`；
- 正文是**问题分析而非知识**：指出与既有页面的重复/命名冲突/内容张力/覆盖关系，并给出处理建议，高频词包括「需人工确认/人工判断/建议/可能重复/命名冲突/张力/消歧/核查」；
- 体积极小（实测 400–700B）。

**实测分布**（约 90–100 个）：`queries` 35、`entities` 29、`concepts` 19、`findings` 4、`controversy` 1、`sources` 1。
按问题类型：重复/已存在 40、内容张力/冲突 32、消歧/核查 23、覆盖/更新 19、命名冲突 6。

## 二、修复总原则

1. **以文档内描述为准**：批注里写的处理建议，就是修复目标本身。
2. **批注中的「需人工审核 / 人工确认 / 用户决定」字样不构成阻塞**——维护任务已获授权，Agent 直接执行判断与修复，不要反过来询问用户。
3. **处理完删除批注页**，把结论落到目标页面；wiki 中不留批注痕迹。
4. **涉及知识缺口、文档缺失、内容矛盾与张力时必须联网核实**（见第五节）。
5. 全程先备份到 `.llm-wiki/repair-backup/`，可回滚。
6. **最终必须清零**：修复完成后，wiki 仓库内**不得残留任何批注文件**（A 类占位页与 B 类分析批注页都必须删除，结论已落到目标页）。验收标准 = 复跑 `audit.py` 的 **H 类「问题批注文档残留」为 0**；未清零即视为修复未完成。

## 三、A 类（占位页）修复决策树

对每个占位页，按顺序判定：

```
① 是否存在同义真实页？（归一化 key 命中，且排除占位页自身）
   └─ 是 → 删除占位页；全 wiki 重写指向占位 slug 的 [[链接]] → 真实页 slug
        （典型：pre-act → entities/preact、prompt-tuning → queries/prompt-tuning）

② 无真实页，且标题是「待办批注/描述性文字」而非知识实体？
   （如「这里可以加入与其他模型的对比」「注意力机制相关概念页缺失qk矩阵相乘」）
   └─ 是 → 删除占位页；指向它的链接降级为纯文本；按批注意图判断是否需要补建真实页

③ 无真实页，且标题是真实知识实体/概念？（如 adapter、agent-ecosystem、三种通信协议对比）
   └─ 知识缺口 → 补建真实页面：
        · 先从 wiki 内既有页面收集素材（相关 concepts/entities/sources 页）
        · 素材不足或需权威事实 → 联网检索（第五节）
        · 按 schema.md 规范写 frontmatter（type/title/created/updated/tags/related/sources）
        · 删除占位页；重写指向它的链接 → 新页 slug

④ 对比/综合类缺口（形如「X-与-Y-对比」）
   └─ 优先用 wiki 内 X、Y 两页内容做对比生成（页面间对比即可解决，不必联网）；
      若 wiki 内信息不足 → 联网补充后再生成
```

## 四、B 类（分析批注）修复决策树

```
① 重复 / 可能已存在
   ├─ 核对两页内容确为重复 → 按合并流程融合（union sources/tags/related，正文择优）
   └─ 非重复（分工不同）→ 在两页加交叉引用与分工说明
   → 删除批注页

② 命名冲突 / 命名碰撞 / 命名张力
   ├─ 同名异义 → 在既有页顶部加消歧说明（如「本页指…；另有 [[X]] 指…」）
   └─ 命名不规范 → 按 references/naming.md 重命名 + 全 wiki 重写链接
   → 删除批注页

③ 内容矛盾 / 张力 / 潜在冲突  ★需联网
   → 检索权威资料核实事实 → 修正页面表述：
     已明确的可判定为更正；仍有争议的保留双方并标注来源（"（来源A）… /（来源B）…"）
   → 删除批注页

④ 覆盖 / 更新（批注称「应以本次内容覆盖既有页面」）
   → 用批注描述的新内容更新既有页面（union sources，不丢旧来源）
   → 删除批注页

⑤ 消歧 / 核查（「需核对」「需确认适用范围」）
   → 按批注给出的假设逐条核对，落实为页面中的适用范围说明或修正
   → 删除批注页
```

## 五、网络检索介入条件（强制）

以下情形**必须**联网检索后再修复，不得仅凭 wiki 内部信息推断：

- 批注指出**知识缺口 / 文档缺失**（需补建真实页面但 wiki 内无素材）；
- 批注指出**内容矛盾与张力**（需权威事实裁决）；
- 补建页面涉及**具体事实、版本号、发表时间、指标数值**等易错信息。

**环境前置检查（强制）**：启动 wiki 修复任务**之前**，先确认当前环境存在可用的网络检索工具。

- 探测方式：用环境中实际可用的检索能力做一次最小查询（不写死具体工具名——不同环境可能是不同的检索后端）。实际执行时按当前环境提供的检索工具调用。
- **若环境中不存在可用的网络检索工具 → 立即停止修复任务并向用户发送警告**，不要降级为"凭记忆编造"，也不要反复重试。

## 六、批量检测

```
python scripts/scan_problem_annotations.py --root <wiki或项目根>
```

输出分类清单（A 类按 ①②③ 分流、B 类按问题类型归档），供修复计划使用。

## 七、注意事项

- 占位页的 `## Related` 常互相指向其他占位页，形成孤岛链——批量处理时按链整体清理。
- 删除占位页后务必重写指向它的 `[[链接]]`（否则产生新的失效链接）；若目标无法补建，则降级为纯文本并记入知识缺口清单。
- B 类批注页可能是**唯一记录某问题的地方**——删除前先把结论写入目标页面，避免信息丢失。
